# 指标（阶段 8 T8.3）

> 这里的数字都是从库里现算的，口径写清楚——面试时能对着 SQL 解释每一个分子分母。
> 复算脚本：`.cache/metrics.mjs`（`node .cache/metrics.mjs`）。

## 1. 三个核心指标

统计时间：2026-10-19（库内真实数据，含 20 条抽取测试集 + 演示数据 + 真机操作）

| 指标 | 目标（PRD 1.3） | 实测 | 口径 |
|---|---|---|---|
| 抽取成功率 | ≥ 80% | **90.2%**（37 / 41） | `extraction_log.status`：`confirmed / (confirmed + failed + rejected)`。<br>`draft`（抽了草稿但用户还没做决定）不计入分母，避免"点了不动"拉低指标 |
| 录入耗时中位 | ≤ 15 s | **1.12 s**（模型往返） | `extraction_log.latency_ms` 中位数。<br>**只含 LLM 往返**，不含人读卡片、点确认的时间；端到端耗时靠真机手测（说话到入库约 8–12 秒，取决于确认速度） |
| 提醒处理率 | ≥ 70% | **80.0%**（4 / 5） | `alert.status`：`(done + discarded + ignored) / 全部`。<br>样本很小（5 条），只能说明"会用/会处理"，不能当统计结论 |

明细：

```json
抽取 { draft: 10, confirmed: 37, rejected: 4 }     成功率 90.2%
耗时 { 样本 37, 中位 1121ms, 最小 873ms, 最大 1584ms }
提醒 { pending: 1, done: 4 }                        处理率 80.0%
```

## 2. 一致性自检（比"指标好看"更重要）

| 检查 | 结果 | 意义 |
|---|---|---|
| 负库存 / 已结束但数量不为 0 的批次 | **0 条** | `consume`/`discard` 在事务里夹住了「扣到负」和「扣完没关批次」两种情况 |
| `stock_log` 条数 | 15 | 每次数量变化都有一条流水，能倒推出当前数量 |
| 平均每个物品的批次数 | 1.10 | 批次表在用（同一物品可以有多个不同到期日的批次），没有被压成"一个物品一个数量" |
| 同一 `client_op_id` 重放 | 幂等（smoke 第 5 节硬断言） | 重试不会多扣一次 |

## 4. 怎么解释这些口径（面试用）

- **为什么成功率分母不含 draft**：这个系统里"抽了草稿"和"用户确认了"是两件事；
  草稿停留只说明用户没继续操作，不代表模型错了。把 draft 算进分母会把"没点"误判成"抽错"。
- **为什么耗时只报模型往返**：端到端耗时里有人的思考时间，无法从日志里客观测量；
  模型往返是系统能保证的部分，也是同类产品常被质疑的部分（1.1 s 属于可用区间）。
- **为什么提醒处理率样本只有 5**：自用系统真实提醒量就小。这里给的是机制验证（能处理、处理完库存和流水对齐），
  不能当统计结论——样本量小就是小，不硬编一个大数字。
